# Releases

Users install prebuilt binaries with the command in [README.md](README.md) and update with `rstop update`. All public commands use the `rstop` executable. There are no package-manager publishing jobs or companion updater binaries.

## CI/CD

Two workflows are maintained:

- [Checks](.github/workflows/checks.yml): main/PR builds test Linux, macOS and Windows, including the public CLI, recording/exports, generated documentation and archive validation. Formatting and Clippy run on Linux. Tags run the Linux gate before building all six release archives; they do not repeat the macOS/Windows test suites.
- [Release](.github/workflows/release.yml): generated by cargo-dist 0.33.1. Pull requests validate the release plan. A version tag builds Linux x86-64/ARM64, macOS Intel/Apple Silicon, and Windows x64/ARM64 archives, generates shell/PowerShell installers and SHA-256 checksums, and publishes a GitHub Release with build attestations. Archives contain project/dependency licenses, the manual, and shell completions.

Every native platform then installs its candidate through the generated installer, verifies its architecture/checksum/receipt, exercises the public CLI and starts/exits the interactive terminal. All six must pass before publication. After publication, the same checks use public download URLs and exercise updates from the previous stable release. [Installation checks](.github/workflows/install-checks.yml) can also verify the latest public version manually without rebuilding it.

Dependency licenses are generated once in the tag's Linux gate from the complete locked dependency graph, then shared with all six archive builds. Normal main/PR checks do not run the collector, and the platform builders do not install it.

Native build runners are Ubuntu 22.04 (both architectures), macOS 15 ARM/Intel, and Windows Server 2022 x64/Windows 11 ARM. A successful build does not establish real-device feature coverage; see [COVERAGE.md](COVERAGE.md).

Release installers and the update library are provided by [cargo-dist](https://axodotdev.github.io/cargo-dist/book/) and [axoupdater](https://github.com/axodotdev/axoupdater). Normal monitoring checks GitHub quietly on launch and every 15 minutes; results are not cached. Only a newer stable release opens the update dialog, with upgrade selected by default, a Release link, session ignore and a persistent version skip. The check has an eight-second deadline and is disabled in read-only/replay sessions or with `check_updates = false`. Installation starts only after the user chooses upgrade, pins the displayed tag and requires the current executable's install receipt. CLI checks/updates remain available with `rstop update --check` and `rstop update`. Source builds and manually moved executables cannot overwrite a separately installed copy.

## Publish

1. Enable GitHub Actions for `fan-ziqi/rstop`. The workflow uses its built-in `GITHUB_TOKEN`; no npm, Homebrew, signing-server, or custom repository credentials are required.
2. Update the package version, lockfile, changelog, and version examples. Regenerate command documentation if the CLI changed:

   ```sh
   cargo build --locked
   python3 scripts/distribution.py docs --binary target/debug/rstop
   dist generate
   python3 scripts/distribution.py workflow
   dist generate --check
   python3 scripts/distribution.py workflow --check
   dist plan
   ```

3. Run the checks below, commit the intended changes, and ensure the main-branch checks pass.
4. Push the matching version tag, for example:

   ```sh
   git tag v0.1.1
   git push origin v0.1.1
   ```

Wait for all six archive jobs and release publication to succeed. Verify the remote branch/tag point to the intended commit. Installation URLs become usable after the release publishes; local fixture tests do not verify this public path. Publishing to crates.io is optional and is not part of the installer release flow.

## Local verification

Install the pinned maintainer tools from their upstream releases: `cargo-dist` 0.33.1 and `cargo-about` 0.9.2. End users need neither tool.

```sh
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
cargo about generate --locked --fail packaging/licenses.hbs -o THIRD-PARTY-LICENSES.html
dist generate --check
python3 scripts/distribution.py workflow --check
dist build --artifacts local --target x86_64-unknown-linux-gnu
python3 scripts/distribution.py archive --directory target/distrib --target x86_64-unknown-linux-gnu
dist build --artifacts global
```

Use the matching target when checking on another host. Archive verification checks the checksum, required license/documentation files, and packaged executable's public commands, recording/replay, exports, and update guards. The checks operate only on owned temporary files. The generated installer can be tested with its `RSTOP_DOWNLOAD_URL` override against a local fixture server; fixture success is not a live release/update-service acceptance claim.

Keep `release.yml` generated: modify [dist-workspace.toml](dist-workspace.toml) and [.github/dist-setup.yml](.github/dist-setup.yml), then run `dist generate` followed by `python3 scripts/distribution.py workflow`. The second command adds the required installation-success condition omitted by cargo-dist 0.33.1; CI checks that guard. Do not hand-edit generated workflow contents. Linux releases use glibc to support dynamically loaded GPU drivers; do not add a static musl build without verifying its actual GPU behavior.

## Check a published installer

Download from the same URL users run and install under an isolated home:

```sh
scratch=$(mktemp -d)
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/fan-ziqi/rstop/releases/latest/download/rstop-installer.sh -o "$scratch/install.sh"
HOME="$scratch" XDG_CONFIG_HOME="$scratch/.config" RSTOP_NO_MODIFY_PATH=1 sh "$scratch/install.sh"
HOME="$scratch" XDG_CONFIG_HOME="$scratch/.config" "$scratch/.local/bin/rstop" --version
HOME="$scratch" XDG_CONFIG_HOME="$scratch/.config" "$scratch/.local/bin/rstop" update --check
```

Verify the release's archive checksum, installer receipt/version, repeated install, and a read-only snapshot. Check the PowerShell installer and archive URLs as well; a Linux install is not Windows/macOS execution acceptance. Preserve actual run URLs/statuses separately from the release instructions.
